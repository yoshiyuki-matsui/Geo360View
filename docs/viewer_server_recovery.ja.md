# Webビューアのサーバ残存と復旧

## 確認された事象

自宅のUbuntu / QGIS 3.44.7環境で、パネルのプレビューは正しいのにWeb側の画像が起点のままになる事象がありました。残存するビューアサーバを停止して起動し直すと、正しい画像になりました。

これはサーバ再起動で改善したという確認結果です。最初にサーバが残った終了操作は未特定です。別途、全体イベントフィルタを外した候補ではQGISのクラッシュが再現しなくなったと報告されています。

## 終了・更新の条件

| 操作・条件 | コードから分かる挙動 | 確認事項 |
| --- | --- | --- |
| Geo360Viewのメニュー「終了」、New Job | 自分のQProcessを停止する | PIDと待受ポートが消えるか |
| パネルの「×」 | UIだけ閉じ、セッションとサーバを残す設計 | 残存はこの操作では正常 |
| ブラウザを閉じる | QGIS側サーバの終了操作ではない | QGISの「終了」で止める |
| 無効化・正常なリロード | `unload()`が呼ばれれば停止する | リロード機構が実際にunloadしたか |
| QGISの通常終了 | 新候補では`aboutToQuit`でも停止する | QGIS終了後のPIDを確認 |
| QGISのクラッシュ・強制終了 | Pythonの終了処理が実行されない場合がある | 新候補の親接続監視で停止するか |
| 実行中のプラグインへの上書き更新 | ファイル交換だけでは実行中サーバのコードは更新されない | 更新前にQGISとサーバを終了する |
| 以前の起動・別QGISインスタンス・手動起動のサーバ | 現在のプラグインが停止できるQProcessとは限らない | 所属とPIDを確認して停止する |

## 0.5.6候補の対策

最新版の候補では、対話操作の待ち時間を守るためFFmpegの自動フォールバックを外しました。OpenCVが異常な位置を返す環境では、新しいフレームの抽出はエラーになります。以前のフォールバック付き候補で表示できたことは、OpenCV自体が修復されたことを意味しません。OpenCVの環境差調査はサーバ残存対策とは別に必要です。

- 起動時の`app.py`と関連モジュールの指紋、設定パス、PID、起動元識別子をhealth APIに追加します。ファイル交換後も実行中プロセスの指紋は変えません。
- 現在のインスタンスが起動した、同じコードのサーバだけを再利用します。古いサーバや別のサーバを検出したら、設定を上書きせず起動を中止して案内します。
- LinuxではQGISからサーバへ開いた標準入力パイプが閉じると、サーバが終了します。Windows比較用候補ではこの監視を無効にして起動問題を切り分けています。手動起動にも監視を適用しません。
- 通常停止はパイプを閉じて終了を待ち、応答しなければ`terminate()`、最後に`kill()`へ進みます。停止できなければ参照を保持し、PIDを通知します。

旧版サーバには親接続監視がありません。候補版をインストールする前に一度停止してください。OSの入出力待ちなどでプロセス自体が停止できない場合は、監視だけでは解消できません。

Windows比較用候補でも、プラグインの終了・unload・QGISの通常終了で、自分が起動したサーバを停止する処理は有効です。ただしQGISのクラッシュ・強制終了時には、サーバが残る可能性があります。標準入力監視がWindowsの起動問題の原因と確定したわけではなく、直接起動との差を調べるための比較です。

## Ubuntuでの確認・手動停止

以下はGeo360Viewのポートが8182の場合です。設定を変更している場合は読み替えます。まずQGISとビューアを閉じます。

```bash
curl --max-time 3 http://127.0.0.1:8182/api/health
ss -ltnp 'sport = :8182'
ps -u "$USER" -o pid,ppid,stat,etime,args | grep -E '[q]gis|[3]60viewer/app.py'
```

終了前にも同じ情報を保存すると、どの操作で残ったか比較できます。旧版healthにはPIDや指紋がありません。`config`がGPXVideoProcessorを指す場合は、そのサーバです。

表示されたPIDの実行パスを確認します。以下の12345は実際のPIDに置き換えてください。

```bash
ps -p 12345 -o user,pid,ppid,stat,args
```

自分のユーザが実行する対象の`Geo360View/360viewer/app.py`であり、使用していないサーバであることを確認したら停止します。別のQGISで使用中なら、そちらから終了します。

```bash
kill -TERM 12345
ps -p 12345 -o pid,stat,args
ss -ltnp 'sport = :8182'
```

しばらく待っても残る場合だけ、PIDと実行パスを再確認して強制終了します。

```bash
kill -KILL 12345
```

`pkill python`などで無関係なPythonをまとめて終了しないでください。`STAT=Z`は終了済みのゾンビで、動いているHTTPサーバとは異なります。

誤生成したキャッシュがある場合は、サーバ停止後に**出力先の`viewer_cache`だけ**を別名へ退避します。`images`、スナップショット、動画、`tmp.gpkg`は削除しません。その後QGISからサーバを起動し直し、途中フレームのプレビューとWeb画像を比較します。

## Windowsでの確認

PowerShellで待受PIDと実行内容を確認します。

```powershell
Get-NetTCPConnection -LocalPort 8182 -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess
Get-CimInstance Win32_Process -Filter "ProcessId = 12345" | Select-Object ProcessId,ParentProcessId,ExecutablePath,CommandLine
```

自分が使用していないGeo360Viewサーバと確認できたPIDだけを、タスクマネージャーの「詳細」で終了します。GPXVideoProcessorや他のPythonプロセスと区別してください。

## 再現時に記録する項目

- QGIS・プラグインの版、OS、使用ポート。
- 終了メニュー、パネルの×、QGIS通常終了、クラッシュ、リロード、上書き更新のどれを行ったか。
- 操作前後のhealth、PID、PPID、実行パス、待受ポート。
- 残存サーバが現在の起動で作られたものか、以前から存在したものか。
- サーバ再起動だけで改善したか、キャッシュ退避も必要だったか。

## 検証状況

終了処理の分岐、旧版・別インスタンス・更新前のサーバを拒否する処理、実際の子プロセスで標準入力EOF後に終了する処理を自動テストしています。テスト環境ではネットワーク待受を許可されないため、子プロセステストのHTTP待受部分だけを代替しています。QGISのQProcessとWindowsでの異常終了・リロード・更新の検証は未実施です。

参考: [Qt QProcess](https://doc.qt.io/qt-6/qprocess.html)、[Python socketserver](https://docs.python.org/3.12/library/socketserver.html)。
